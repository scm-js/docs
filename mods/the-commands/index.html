The commands

What a mod is#

scmjs mod info "Cosmonarchy BW"

Cosmonarchy BW
A mod for StarCraft 1.16.1, from a folder of the game's files

  Files            7,769 · 931.1 MB
  Kinds            11 tables (748 KB), 13 scripts (2.0 MB), 3,894 pictures (254.1 MB), 3,527 sounds (553.1 MB), …
  Tables           flingy.datex, images.datex, mapdata.datex, orders.datex, portdata.datex, sfxdata.dat, …
  Extended         flingy.datex: 1,000 entries (the game's 209), GPTP's .datex layout
                   …
                   units.datex: 3,000 entries (the game's 228), GPTP's .datex layout
  Plugins          _qdp-hotloader.qdp (358 KB), aise.qdp (1.0 MB), gptp.qdp (5.9 MB), … — kept, not run
  FireGraft        1161.fgd (555 KB), Cosmonarchy BW.fgp (98 KB) — kept, not applied
  Exe              Cosmonarchy BW.exe: FireGraft's patcher with 1 plugin (id fc724f8c, 358 KB), its archive at byte 804,352
  Layers           Cosmonarchy BW.exe then mpq
  Hash             ac3f86533e4b5a31
  Without plugins  b13e467fb5abb298 (a page that runs none of the plugins)

It takes a folder (the game's paths at its root or in a folder under it, as a release keeps them under mpq/), an .mpq, a mod's .exe or a .zip. A folder's own archives and exes are read too, archives first and loose files over them, the later winning, as the game lays its own archives. A self-executing exe is read for the archive appended to it, never run: MPQDraft's self-executing MPQ, or FireGraft's patcher with its plugins listed. A zip's stored and deflated members are read; a zip64 or encrypted zip is not. An archive's list of its files is taken as its files; an archive with no list is searched for the names the game reads. A name the list holds and the archive does not (Cosmonarchy's loader lists six tileset files it never packed) is left out and said.

A copy of the game in the folder is not the mod. Some downloads carry the whole game the mod runs on beside the mod itself; a folder that holds a StarDat.mpq is taken for such a copy, and its own archives (StarDat.mpq, BrooDat.mpq, patch_rt.mpq, StarCraft.mpq, BroodWar.mpq) and everything under its Maps folder are left out; a ▲ line names the archives among them. Anything else in it, a mod's own archive or exe put there for one, is read as before. A folder that holds only a copy of the game is refused. A single patch_rt.mpq named by itself, the form some older mods ship in, opens as a mod.

The last two lines are the mod's hash. An Older hash line follows them when the mod holds files an operating system left in its folders (desktop.ini, Thumbs.db, .DS_Store): the hash it had while those counted.

A folder to edit#

scmjs mod unpack MyMod.mpq mymod

✔ My Mod: 1,018 files · 41.3 MB · → mymod
  As text        11 tables, 6 string tables, 1 iscript, 2 AI scripts, 96 overlay files
  As pictures    832 GRPs (the jungle palette)
  As they are    70 other files
  Names          from the mod's string tables

--palette badlands draws the sheets in another tileset's palette. Unpacking over an earlier unpack replaces its folders and leaves anything you added beside them.

Back into an MPQ#

scmjs mod pack mymod                    # mymod.mpq beside the folder
scmjs mod pack mymod -o MyMod.mpq --compression pkware
scmjs mod pack mymod --folder samase/   # the files loose in the game's paths

The MPQ has a file list and is compressed with zlib by default (pkware is what Blizzard's own tools wrote, none stores the files). The same folder packs into the same bytes every time. A sound under sounds/ that is not a WAV (an Ogg, an MP3) is converted to one with ffmpeg, when ffmpeg is on your PATH. Files outside the known folders are left out and named.

Looking for mistakes#

scmjs mod check mymod

My Mod · ✖ 2 errors (over StarCraft 1.16.1 (2 archives))
  ✖ units 1 (Terran Ghost) ground_weapon: points at weapons 200, past the 130 entries weapons.dat has
  ✖ images 5 grp_file: names unit\custom\nothere.grp, which is in neither the mod nor the game: the game stops when it draws it

Errors are what makes the game stop or draw nothing: a reference past its table (a unit's weapon, flingy or subunit, a flingy's sprite, a sprite's image), a string past its string table, an image with no GRP or overlay file, an image whose animation script is missing, a button set or requirement for something the tables do not have. Warnings are what is probably a mistake: a weapon or animation script the mod added that nothing uses, a sound row the mod changed whose file is nowhere, units with the same name, tables in both DatExtend's and GPTP's layouts. What the mod leaves as the game had it is not judged; the game has leftovers of its own. The check runs over your copy of the game when it finds one; without one, references to the game's own files are not looked at, and it says so. It exits 1 when there is an error.

A changelog#

scmjs mod diff mymod             # what the mod changes in the game
scmjs mod diff v1.mpq mymod      # what changed between two versions

StarCraft 1.16.1 (2 archives) → mymod · 6 changes

Tables
  Terran Marine: ground weapon damage 6 → 7
  unit 228 added: Terran Maverick
  sound 69 → Bullet\TGoFir00.wav

Animation scripts
  iscript: Terran Marine's GndAttkRpt animation changed

Pictures
  3 pictures changed, 1 added

A weapon's change is told through the units that carry it, a sound row's by the file it plays, an animation script's by the unit drawn with it and the animation that changed. With one mod, the other side is your copy of the game.

Starting a mod#

scmjs mod new mymod --name "My Mod"

writes mod.json and a README of one paragraph. Put the game's files you change under files/ at their paths (files/arr/units.dat), or the texts in their folders, and pack. Starting from an existing mod is mod unpack.

Check, then pack#

scmjs mod build mymod -o MyMod.mpq

runs mod check and, when it finds no error, mod pack with the same options. --force packs anyway.

Playing it#

scmjs mod play mymod --map "(2)Ridge.scx"

opens the play page in your browser and hands it every file of the mod, its plugins and FireGraft files with them, and the mod's hash; the page keeps the files that differ from your copy of the game. With --map the map starts with the mod. The hand-over is described in the command line's guide.

scmjs mod play "Cosmonarchy BW" --map "(4)Exodus 1.0.scx" --bot cosmonarchy-example

--bot puts a community bot on the other side: one of the play page's bots by its key, or a .scmbot file you built. The map waits on the page's setup screen with the bot in the row beside yours, saying whether it was made for the mod, and you press Start Game; --start starts it at once. --race sets the bot's race: zerg, terran, protoss or random, or a race the mod's mod.json names, by its name or its number. The page's own bots need a scmjs.dev account, and the page asks you to sign in; a file of your own does not.

The mod's hash#

A mod goes by a hash of sixteen hex digits, worked out the same way by the play page, scmjs mod info, the editor's data sets and the tools that read a replay of the mod, so one mod has one hash everywhere. It covers every file the mod provides: each file it lays over the game, loose under its game folders or inside its archives (an .mpq, or the archive inside a FireGraft or MPQDraft loader .exe), each plugin it carries as a file, and its FireGraft project (.fgp). It is never compared with anyone's copy of the game, so two people with different copies give the same mod the same hash, and a release unpacked into a folder and packed again keeps it. Left out are what is not the mod's files: a file an archive lists and does not hold, a folder's read-mes, programs and libraries, and FireGraft's database (.fgd). A page that does not run the plugins plays something else, so beside the hash there is one without the plugins; mod info prints both, and a page that runs none of them presents that one. Each file is a line, its name and the SHA-256 of its bytes, and the hash is over the sorted lines (the exact form).

Files an operating system leaves in folders are not the mod's. Windows Explorer writes desktop.ini and Thumbs.db into folders it has shown, the macOS Finder .DS_Store, and a mod's loader that packs its folder into an archive packs them in too. The game never asks for them, and not every way of reading a folder hands them over: a browser's folder picker never shows desktop.ini or Thumbs.db, while a dropped folder and the command line do. So they have no line in the hash, wherever they lie, and the same mod has the same hash however it was read. They are, by name in any case:

Name What leaves it
desktop.ini Windows Explorer, a folder's view and icon
Thumbs.db, ehthumbs.db, ehthumbs_vista.db Windows Explorer and Media Center, thumbnails
.DS_Store, Icon followed by a carriage return the macOS Finder, a folder's view and icon
a name that starts with ._, and everything under a folder __MACOSX macOS, the second half of a file on a disk that is not its own, and the folder its zips keep those in
.directory KDE's file manager, a folder's view

A file whose name only holds one of these (mydesktop.ini, thumbs.db.txt) is a file of the mod like any other. So is every other file a browser's folder picker does not show. Chrome hides more than the two names above: shortcuts (.lnk, .url, .scf), names Windows keeps for devices (aux.wav, con.grp), and names that begin or end with a space or ~ or end with a dot; on Windows its list of file types it does not hand to a page adds .ini, .cfg, .dll and .manifest. Those may be a mod's own (a plugin's config.ini), so they keep their lines: a mod read through the folder picker is short of them, and its hash says so by being another. Read such a mod with scmjs, or drop its folder on the editor or the play page: a dropped folder is read whole.

The hash before 9 November 2026 had lines for those files, so a mod whose folder holds any had another hash then: Cosmonarchy's release, with a desktop.ini in two of its sound folders, was 1c41a2d7701fe842 and is 20e1c6d89ae2af75. A replay saved before that date, and a mod a browser kept, name the mod by the older hash. It is still taken wherever hashes are compared, where it can be worked out: mod info prints it as Older hash, the replay commands accept it, and the play page finds a mod it kept under the older hash by the new one and plays an older replay with it. It cannot be worked out by a route that never saw the files: a folder chosen with the browser's folder picker has no older hash, so a replay saved before the date is not matched to it. Drop the folder on the play page instead.

Testing with it#

scmjs mod test mymod ridge.scx
scmjs map test ridge.scx --mod mymod
scmjs map trace ridge.scx --mod MyMod.mpq

The game engine's runners play a map with the mod's files laid over the game's, fetched from the play page once like any command that plays the game. These three lay the mod's files only; its plugins and FireGraft project run beside a bot in scmjs bot run and bot ladder (a bot for your mod). A scenario with a bot on the other side is not there yet.

Replays of modded games#

A replay holds the players' commands, not the files the game read. Played back with other files, the same commands make another game: a unit costs something else, a building is somewhere else, and the replay goes its own way. So a replay of a mod says which mod it was. scmJS adds a short section at the end of the file, after what the game wrote, that holds the mod's name, its hash (with its plugins, or without them when the page ran none), its makers' link, the plugins that ran and the FireGraft patch applied. StarCraft itself does not read it: 1.16.1 plays the file as it would the same file without it, and Remastered steps over it as over any section it does not know. The replay package's read-me has the bytes.

What reads it:

  • scmjs replay info shows it on the Mod line. With --builds it lists what each player ordered, by id until --mod names the mod's folder, and then with the mod's names and costs. A mod whose data set is not the one the replay names is refused. A player of a race the mod adds is named by the section's races when it has them, else by the races of the mod's mod.json with --mod, else Race and the number.
  • scmjs map trace --replay and map cost --replay need the mod named with --mod and check it the same way. A game the mod's plugins ran in is refused, as the engine's runners do not run plugins.
  • scmjs replay watch, replay export, map heatmap, map coverage and map test record refuse a mod's replay, or leave it out of a list, for now.
  • The play page plays it with the mod it names, switching to that mod when your browser keeps it, or saying which mod it needs and where its makers publish it (On the play page).
  • The Aftermath plugin, the editor's replay viewer, shows the mod and its link, plays the replay with the mod your browser keeps, and takes the names and costs from the mod's folder when you attach it (Replays of a mod).

The play page writes the section into every replay it saves of a game of a mod: Save Replay, and Watch the Replay and Analyse in the Editor at the end of a game. A replay StarCraft itself recorded with a mod has no such section. On the play page, choose the mod under Mods first; the page then asks whether to watch the replay with the mod or without it. Such replays are expected to play, but none has been checked yet.

A bot for your mod#

scmjs mod header "Cosmonarchy BW" --out mybot --bot

A community bot made for a mod names the mod's units, weapons, upgrades and technologies, which BWAPI's own names (Terran_SCV) do not cover. mod header writes them for it: <Mod>.h, C++ for a bot built with scmbot (Cosmonarchy_BW::UnitTypes::Terran_Mason is a BWAPI::UnitType), and <Mod>.ids.json, the same ids and names for bots and tools in other languages. Every name the mod has is there, not only the ones it added, since a mod may rename everything. Both files carry the mod's name and its hash. With --bot, --out is the bot's folder and its scmbot.json gains the mod; scmbot build writes it into the .scmbot file, and when the bot plays, the runners say "made for" the mod when the game's mod is that one, "plays vanilla data" for a bot made for no mod, and warn (the game still plays) for a bot made for another. The scmbot repository's examples/cosmonarchy/ is a small bot for Cosmonarchy written against such a header. See the command for the names' rules. To try a bot on the mod without a page, scmjs bot run mybot/out/mybot.scmbot "(4)Exodus 1.0.scx" --mod "Cosmonarchy BW" plays it with the mod's plugins, and scmjs bot ladder … --mod plays a ladder on the mod (a bot on a mod).

For AI tools#

scmjs mcp has the mod commands as tools: mod_info, mod_check, mod_diff, mod_unpack, mod_pack, mod_new, mod_header and mod_play. An AI tool can unpack a mod, change a table's text and pack it again, as you would, write the header for a bot, and hand the mod with a map and a bot to the play page in your browser, which it says the link to and what the page answered. map_trace and map_cost take a mod. See AI tools.
