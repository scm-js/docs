A mod as a folder

scmjs mod unpack writes a mod as a folder like this one:

mymod/
  mod.json              the mod's name, version, authors and licence, and what the folder needs to pack
  README.md
  tables/units.txt …    the unit, weapon, flingy, sprite, image, upgrade, technology, order,
                        sound, portrait and campaign tables, as PyDAT's text
  strings/stat_txt.txt  the string tables, as PyTBL's text (images.txt, sfxdata.txt, unitnames.txt …)
  iscript/iscript.txt   the animation scripts, as PyICE's text (a mod may have several)
  ai/aiscript.txt       the AI scripts, aiscript.bin and bwscript.bin, as PyAI's text
  overlays/unit/terran/marine.lob.txt …   the overlay offsets, as PyLO's text
  graphics/unit/terran/marine.png …       each GRP as a PNG sheet
  sounds/sound/…        the WAV files, as they are
  grafts/Units.txt …    GPTP's .graft files (requirements, buttons), as graftc's text
  maps/…                the mod's maps
  plugins/, Firegraft/  plugins and FireGraft files, as they are
  files/…               every other file of the game the mod changes, as it is

The texts are PyMS's own dialects, so a table exported here reads in PyDAT and the other way round, and the same for PyTBL, PyICE, PyAI and PyLO. A few lines start # scmjs:; PyMS reads them as comments, and they keep what the text form cannot say (where the game's own iscript keeps its headers, the order of its table), so the file comes back as it was. Each table entry's header line names it (Unit(0): # Terran Marine), and the AI script names units, upgrades and technologies, with the names from the mod's own string tables, or the game's when the mod has none.

Pictures. Each GRP is one PNG: every frame in a cell of the GRP's size, 17 cells to a row for a unit's facings. The PNG is an indexed picture in a named palette (the jungle tileset's by default, or the one mod.json names; the mod's own tileset\<name>.wpe when it has one, else your game's), with the frame boxes and the palette's name written inside it, so the GRP that comes back is the same bytes. Draw over a sheet in a program that keeps its palette and only the pixels you changed change. A picture saved in full colour is brought to the nearest of the palette's colours when it is packed, and mod pack says how many pixels moved.

What comes back the same. Each file is written as text or a picture only when that text or picture packs back into exactly the same bytes; that check is the packer itself. A file that would not — a GRP another tool encoded, which reads as the same pictures but in other bytes, or a file that is not what its name says — is kept as it is under files/, and mod.json lists it under kept with why. So an unpacked folder packs back into the mod it came from, file for file, and an edit to one text changes that one file.

mod.json holds what a person fills in (name, version, authors, licence, base, the game the mod is for) and what packing needs: each table's file and layout, each string table's text encoding, the palette, where the names came from, the files kept as bytes, the plugins and FireGraft files and whether they were inside the mod's archive, and the sources the folder was made from in their load order (layers). An unpacked mod's names stay as they were (Units.graft, arr\units.datex).

Tables in other layouts. A table may be the game's own size, DatExtend's expanded .dat (PyMS's reading, more entries and a wider flingy column), or GPTP's .datex (more entries again, wider columns, no header). Each is written as text in the same way and packed back in the layout it came in, at the width its text has.

Races a mod adds#

To the game a race is a number: one byte in each player's record, in a map and in a replay. 0 to 7 are the game's own: Zerg, Terran, Protoss, then Independent, Neutral, User Selectable, Random and Inactive. A mod can give its players other numbers, and nothing in its files says what those races are called (the names are in its plugin's code). So the tools keep the number as it is and, until something names it, show it as Race and the number: Race 69 in replay info's player list, in Player Settings and in Statistics.

mod.json names them, under races:

"races": [
  { "id": 69, "name": "Askosi", "letter": "a", "like": 1 }
]
  • id is the race's number, 8 to 255.
  • name is what it is called, up to 40 characters.
  • letter (optional) is the letter the race's own files go by, as game\aconsole.pcx and rez\statbtna.bin do for a.
  • like (optional) is the game's race it plays as: 0 Zerg, 1 Terran, 2 Protoss.

A row with one of the game's numbers, a number an earlier row has, or no name is left out. mod.json is not one of the mod's files, so naming races leaves the mod's hash as it was. It is read at the top of a folder of the game's files as well as in a folder mod unpack wrote, and mod unpack keeps the races when it unpacks a new release over a folder that has them.

mod info lists them, replay info --mod names a player's race by them when the replay does not name it itself, and mod play --race takes one by its name or its number. mod check mentions it when a mod's files suggest races of its own and mod.json names none: strings past the game's own in rez\network.tbl, or a console picture game\<letter>console.pcx or rez\statbtn<letter>.bin under a letter other than z, t, p and n. That is a hint, not a finding: the check fills in no name and fails nothing for it.

In the editor, a data set added from a folder (Help ▸ Game Data… ▸ Add a data set…) takes the races of the mod.json directly in that folder; a plugin can name them too, and a map made with the data set carries them (A map remembers its data set).
