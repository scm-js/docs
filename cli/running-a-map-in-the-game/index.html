Running a map in the game

These commands start the map in the game itself, the engine of the play page, with the game's files from your copy of StarCraft (what they need). Nobody has to play: the game runs as fast as the computer can run it. Or the players of a recorded game play it: --replay gives the game the commands from a replay, so the game in a bug report can be traced and tested. A map in the original StarCraft 1.00 form is run as Brood War, as the editor would convert it. The Blizzard campaign maps are not something the engine runs yet. Each command exits with 2 when the game could not start.

Which triggers fire#

scmjs map trace starts the map as a Use Map Settings game, with your seat left idle and the computers as the map sets them, runs it for a while, and records every condition the game checks and every action it runs. The report has a line per trigger, with how often it fired, when first and last, and whose it is. Then come the triggers that never fired, each with the condition that last said no.

scmjs map trace ums.scx. Nobody brings a Marine to the middle, so the trigger waiting for one never fires.

The game runs the triggers about every two seconds; each run is a pass, and a trigger that fires on every pass is a preserved one. A count with +n after it is a trigger whose Wait held it and then let it go on n times.

Option What it does
--frames How long to run, at 24 frames a second. The default, 2,400, is 100 seconds of play; the game may end sooner if a trigger ends it
--seed Fixes the game's luck, so the same map and seed give the same run
--all Lists every trigger, when the map has more than forty
--json The same, per trigger, as data

Nobody plays, so nothing a player would do happens. A trigger waiting for a unit to be brought somewhere will say so, which is the point.

What the triggers cost#

scmjs map cost runs the map the same way and weighs every trigger the game passes and every condition and action it runs, as StarCraft: Remastered charges for them. The model is the one TrigScript's editor uses, measured on the real game: a Deaths condition costs about five nanoseconds, and the game stays smooth up to about fifteen milliseconds of triggers a frame. The report says what a frame costs on average where triggers ran and at most, how that compares with what a frame can carry, and which triggers cost the most:

✔ trigscript-frame-cost.scx: triggers cost 0.025 ms a frame on average where they ran (599 of 601 frames), 1.10 ms at the most (frame 2: 83,787 records, 53,192 triggers)
  Remastered on a fast computer: smooth to about 15 ms of triggers a frame, slows past 37 ms
  83,787 of the records ran in no trigger of the map — a program's own (TrigScript, eudplib), 1.10 ms in all

A TrigScript or eudplib program runs its own records through the EUD trigger chain rather than through the map's trigger list. For such a map the cost is in the first lines, and the triggers listed are only the ones that start the program. TrigScript's editor shows a program's cost line by line.

Triggers in a replay's game#

When someone sends a replay of a game where the map went wrong, --replay plays that game with the trace on. The players' own commands drive it, people and computers as they played, to the end of the replay.

scmjs map trace --replay report.rep --order

A replay of a mod needs that mod named with --mod, and the command checks that the mod's data set is the one the replay names before it plays. A game the mod's plugins ran in is refused: the engine's runners lay a mod's files over the game's and run no plugin.

The report is the one above, with two differences. The first and last firings are given on the game's clock, m:ss at Fastest as the replay viewer counts it, and only the triggers owned by the players in the game are listed. --order adds every firing in the order the game ran them: the time, the frame, whose copy of the trigger it was, and the trigger.

With no map named, the game is played on the map inside the replay. Name a map as well to play the replay's commands on that map instead, such as the fixed version of the one in the bug report:

scmjs map trace fixed.scx --replay report.rep

The command says first how the map differs from the one in the replay. A replay is only the players' commands, so a changed map can make the game go out of step. When a unit a player clicked is not there, or a building cannot be placed, the game plays on with commands meant for another game. Changes to triggers alone usually keep it in step. Changes to units, terrain or resources usually do not. The game checks each command against what it has, and the report says when and where the game parted from the replay. What fired before that point is what happened.

scmjs map cost --replay weighs the triggers of the replay's game in the same way. --frames stops the game sooner. Left out, the whole replay is played. In a game that is not Use Map Settings, the game runs its own melee triggers rather than the map's, and the report says so.

Testing a map's triggers#

scmjs map test checks that a map's triggers do what you meant, in the game. You write scenarios in a tests file: what the game starts with, what happens at given times, how long to play, and what must be true at the end. Each scenario is one game. A scenario that fails says what did not hold and what was there instead, and keeps the game's replay so you can watch what happened.

scmjs map test ums.scx, with the tests file kept beside the test map.

Here the third scenario found something real: the test map has no ground a Marine can stand on, so the Marine never appeared and the trigger waiting for it never fired. That is why a failed scenario lists the game's own warnings from its start.

The tests file#

The tests are read from <map>.tests.json beside the map (ums.tests.json for ums.scx), or from the files named after the map on the command line. The file is JSON:

{
  "scenarios": [
    {
      "name": "the alarm wins the game",
      "frames": "0:20",
      "steps": [
        { "at": 24, "chat": "glhf" },
        { "at": "0:02", "create": "Terran Wraith", "player": 1, "location": "Middle" },
        { "at": "0:05", "switch": "Alarm raised", "state": "set" }
      ],
      "expect": [
        { "trigger": "Opening", "fired": 1 },
        { "text": "Hold the base." },
        { "units": "Terran Wraith", "player": 1, "location": "Middle", "is": 1 },
        { "switch": "Alarm raised", "is": "set" },
        { "outcome": "victory", "player": 1 },
        { "ended": true }
      ]
    },
    {
      "name": "a Marine brought to the middle raises the alarm",
      "frames": "0:25",
      "setup": [
        { "create": "Terran Marine", "player": 1, "location": "Middle" }
      ],
      "expect": [
        { "trigger": 2 },
        { "switch": "Alarm raised", "is": "set" }
      ]
    }
  ]
}

A scenario has a name, and may have frames, seed, setup, steps and expect. frames is how long to play: a number of frames, 24 to a second at Fastest, or "m:ss"; 2,400 unless the file or --frames says otherwise. frames and seed at the top of the file apply to every scenario that does not set its own.

A scenario may name a replay instead of setup and steps. The replay's commands drive the game, played on the map being tested, and the scenario plays to the replay's end unless frames says otherwise:

{
  "name": "the bunker fills at 7:30",
  "replay": "reports/bunker.rep",
  "expect": [
    { "trigger": "Bunker full", "fired": 1 },
    { "outcome": "victory", "player": 1 }
  ]
}

The path is relative to the tests file's folder. seed does nothing here, because the game uses the replay's own. Such a scenario takes no setup or steps, since anything added to the game would take it out of step with the replay. scmjs map test record writes these scenarios for you (below).

Things are named as the trigger window names them:

Thing Written as
Player A number from 1 to 12, or "Player 1". Where a trigger would take a group, "All Players", "Force 1", "Foes" and "Allies" too
Unit Its name ("Terran Marine", or "Marine" when that is clear), a class ("Any unit", "Men", "Buildings", "Factories"), or its number in units.dat
Location Its name, "Anywhere", or its number
Switch Its name, "Switch 3", or a number from 1 to 256
Trigger The number scmjs map trace prints for it, or the text of its Comment action

A name the map does not have is an error that lists the names it does have.

setup is what the game starts with. Each entry does one thing:

Entry Does
{ "create": unit, "player": p, "count": n, "location": l } Creates the units (one unless count says)
{ "kill": unit, "player": p, "count": n, "location": l } Kills the units (all of them unless count says)
{ "remove": unit, "player": p, "count": n, "location": l } Removes the units, as Remove Unit does
{ "give": unit, "player": p, "to": q, "count": n, "location": l } Gives the units to player q
{ "switch": s, "state": "set" } Sets the switch ("clear" and "toggle" too)
{ "minerals": n, "player": p }, { "gas": n, "player": p } Sets the player's minerals or gas; "+100" adds, "-100" takes away
{ "deaths": unit, "player": p, "count": n } Sets the death count, with the same + and -
{ "action": "Set Countdown Timer(Set To, 60)" } Any action, in the trigger window's text form; a list of them works too

location is Anywhere when left out.

steps happen during the game. Each has at, a frame or "m:ss", and one of the entries above, or one of these, which are your own commands as a player would give them:

Entry Does
{ "at": t, "order": "move", "unit": u, "location": l, "to": m } Orders your units of that type in location l to location m: "move", "attack" (attack-move) or "patrol"; "stop" and "hold" need no to. unit is Any unit and location Anywhere when left out
{ "at": t, "chat": "text" } Sends a chat line, which shows on screen like any other

You play the map's first slot that is open to a person, as when you start the map alone, and the computers play as the map sets them. Your commands reach the game at the frame given. The other steps are carried out by the game's triggers, which run about every 31 frames (1.3 seconds), so they happen at the first pass after the game's clock reaches their time.

expect is what must be true when the scenario ends:

Entry Holds when
{ "trigger": t, "fired": n } The trigger fired that many times; true (the default) is at least once, false is never
{ "switch": s, "is": "set" } The switch is set, or "clear"
{ "deaths": unit, "player": p, "is": n } The player's death count for that unit
{ "minerals": n, "player": p }, { "gas": n, "player": p } The player's minerals or gas
{ "units": unit, "player": p, "location": l, "is": n } How many of the units the player has there, counted as the Bring condition counts them (as Command counts them when there is no location; player is All Players when left out)
{ "text": "words" } The words were on your screen at some point: trigger text, transmissions, chat. "shown": false for words that must not appear. In a replay's game, the screen is the replay viewer's
{ "outcome": "victory", "player": p } The player's game ended in victory ("defeat", "draw", or "none" for no outcome yet)
{ "ended": true } The game ended before the scenario's frames ran out (false: it was still going)

A count is a number, meaning exactly that many, or a comparison such as ">= 2", "< 5" or "!= 0". The text shown and how often a trigger fired cover the whole game; everything else is read when the scenario ends.

How a test runs#

The setup and the timed steps become triggers in a copy of the map. The setup is one trigger placed before the map's own, owned by the first player in the game, with the condition Always, so it runs first in the first pass. Each step is a trigger placed after the map's own with an Elapsed Time condition. Your map file is not changed, and the trigger numbers in the report are the map's own.

Because these triggers are part of the copy, the replay holds them. A failed scenario's replay is kept in <map>.tests/ beside the map (or where --out says) and plays back the scenario exactly as it ran. scmjs replay open opens it in the editor, where the test's own triggers show first and last among the map's.

--clips also keeps a clip of each failed scenario, to see what went wrong without opening the replay: the eight seconds of its game up to the moment it ended, and two more, as replay export draws them, the camera following your units. A clip is a GIF named after the tests file and the scenario, such as ums.tests.a-marine-brought-to-the-middle-raises-the-alarm.gif, in <map>.clips/ beside the map, or in the folder --clips names. --clips-format webm makes WebM files instead. Each clip gets a line after the summary, --json lists them, and --format github, junit and sarif name a scenario's clip in its failure. The clips are drawn in a browser on your computer, as replay export draws, so they need Chrome, Chromium or Edge; without one the command says so once and the result of the tests stands. A scenario that plays a replay has no clip of its own, since its game is that replay.

$ scmjs map test ums.scx --clips
…
✖ 2 of 3 scenarios failed (10.0 s)
  ✔ ums.clips/ums.tests.the-carrier-flies-to-the-middle-which-is-not-a-marine.gif · 228 KB · 0:08 · 0:32–0:40 of the game
  ✔ ums.clips/ums.tests.a-marine-brought-to-the-middle-raises-the-alarm.gif · 254 KB · 0:08 · 0:17–0:25 of the game
  2 clips of the failed scenarios in ums.clips
Option What it does
--clips [folder] A GIF of the end of each failed scenario's game, in <map>.clips/ or the folder named
--clips-format webm The clips as WebM files rather than GIFs
--seed The game's random seed for scenarios that do not set one; the same map, scenario and seed give the same game every time
--frames How long to play, for scenarios and files that do not say
--out Where the failed scenarios' replays go
-u, --update For scenarios that play a replay: the expectations that no longer hold are rewritten to what the game gives now
--json Every scenario with each expectation, whether it held and what the game had
--format github, junit, sarif The failures in the forms CI tools read, as for map check, each placed on the scenario's line in the tests file

The command exits with 1 when a scenario fails, and with 2 when the tests file or the map cannot be read or the game could not start. It needs the game, so it does not run on GitHub's own runners; the workflow scmjs init writes leaves it out and says how to run it on a runner of your own that has the game.

A test cannot yet have a player leave (you are the only person in the game) or give the computers' own commands, except by playing a replay of a game where they did.

A test from a replay#

scmjs map test record turns a replay into a test. It plays the replay on the map, as map trace --replay does, and writes a scenario into the map's tests file with everything the game ended with as expectations:

$ scmjs map test record 1631.scx 1631.rep --name "2v2 to the end"
✔ Recorded "2v2 to the end" into 1631.tests.json · 14,662 frames (10:16) · 40 expectations · 6.5 s
  5 triggers, 1 line shown, 4 outcomes, 1 end, 8 unit counts, 4 minerals, 4 gas, 13 death counts

The scenario it wrote begins:

{
  "name": "2v2 to the end",
  "replay": "1631.rep",
  "frames": 14662,
  "expect": [
    { "trigger": 1709, "fired": 2 },
    { "trigger": 1710, "fired": 2 },
    { "trigger": 1711, "fired": 0 },
    { "trigger": 1712, "fired": 1 },
    { "trigger": 1713, "fired": 4 },
    { "text": "ErOs_Class has left the game.", "shown": true },
    { "outcome": "defeat", "player": 3 },
    { "outcome": "victory", "player": 4 },

The expectations are a snapshot of the end of the game: how often each trigger the players own fired (0 for the ones that never did), the switches that are set and the named ones that are clear, the lines shown that were not chat, each player's outcome, whether the game ended, each player's men and buildings, minerals and gas, and every death count. Triggers, switches and units are named as the map names them, where the map has a name for them. Each expectation is one line of the file, so delete the lines you do not care about and keep the ones the test is for.

Option What it does
--name The scenario's name; the replay's file name by default. A scenario with that name is replaced
--tests The tests file to write into; <map>.tests.json beside the map by default, made if it is not there
--frames How much of the replay to play; all of it by default
--json The scenario as written, with the game's end

From then on scmjs map test plays the replay against the map as it is now. After a change you meant to make, scmjs map test map.scx -u rewrites the expectations of replay-driven scenarios that no longer hold to what the game gives now. Only the values change. The expectations you deleted stay deleted, and a comparison such as ">= 3" that still holds is left alone. Scenarios with steps are never rewritten. If the map changed so much that the game parted from the replay, the report says when, as map trace --replay does.

Which triggers fired across many games#

scmjs map coverage plays a folder of replays on the map, each as map trace --replay plays one, and adds up what fired. It answers whether a trigger ever fires when people play the map. A trigger that never fired in any of the games is either one nobody reaches or one that is broken, so those are listed clearly.

scmjs map coverage td.scx replays/

Replays are files or folders, sub-folders included. Only replays of this map count: the same map, or one with the same name and size, as for map heatmap. Only Use Map Settings games count too, since in the other game types the game runs its own melee triggers. Every replay left out is listed with the reason. Several games are played at once: half the processors, at most four, or --parallel.

--force took replays played on other maps, so five of the six games parted from this one early. Only the last game ran this map as it was played.

For each trigger the table gives the games it fired in, how often it fired in all of them, and its first firing on the game's clock. Only triggers owned by a player in at least one of the games are listed. The first line counts the rest separately, and --all lists them too. A game whose players' commands parted from the map, as explained above, counts only what fired before that point, and is marked ▲.

--tests counts the scenarios of the map's tests file as games as well, and a tests file named among the replays (any .json) counts its scenarios. Whether a scenario passes does not matter here; that is map test's job.

Option What it does
--tests Also count the games of <map>.tests.json beside the map
--strict Exits with 1 when a trigger a player owned never fired
--format github, junit or sarif: the triggers that never fired, for CI. Warnings, or errors with --strict, and a note for each game that parted
--all Lists every trigger, even ones no player in the games owned
--force Takes replays played on another map too. Expect those games to part early
--parallel Games played at once
--json Every game, every trigger with its counts, its text and why it never fired

Each replay takes about a second for every minute or two of play, so a folder of a hundred games takes a few minutes. Like the other commands that run the game, it needs your copy of StarCraft, so in CI it runs only on a machine that has one.

A map's layout#

scmjs map analyze reads a melee map's layout without running the game, in about a second: where each start is, its main and its natural, how far every pair of starts is apart on foot beside the straight line, the narrowest points on the way, and how much of the map is walkable, buildable and raised ground. It needs your copy of StarCraft for the map's tileset, which says which ground is walkable and at what height, but not the game engine.

With more than four starts, a table of the ground distances takes the place of the pairs, followed by the shortest and longest pair; --all lists every pair, and every base on the map with whose main or natural it is. --json gives everything as data: the starts, every pair with both distances and the seconds, the narrowest points with their places, the bases, the terrain shares and the verdicts.

How the ground is walked. The map is read as a grid of minitiles, sixteen to a tile, each walkable or not by the tileset, the way the game's own pathing reads it; a grid of whole tiles would close one-tile passages and open cliffs a unit cannot climb. Buildings and resources the map places, pre-placed neutral buildings and the units a doodad brings (doors, traps) stand in the way; units that move do not. A walk keeps one minitile off every wall, about the room a Zergling or a Marine needs, and goes straight or diagonally from minitile to minitile (a diagonal step costing 1.4 straight ones), never across a wall's corner. Walks are measured from start location to start location.

What narrow means. At each point of a walk, the passage is as wide as the shortest straight line through it from wall to wall, across, down or along either diagonal. The narrowest such point on a walk, leaving out the first and last three tiles, is its narrowest point. A patch of unwalkable ground standing on its own and smaller than 16 tiles (a rock, a doodad, a lone geyser) is not counted as a wall, since a unit walks round it on either side; a cliff, a mineral line against it, or a building is.

Islands No ground joins two starts
Mains A start's main has another number of fields or geysers, or other amounts
Naturals A start has none, shares its natural with another start, has one 5 tiles or more farther or nearer than the starts' middle (than the other start's, with two), or has no gas there while others do

Against the game. These walks are not the game's: the game's pathfinder goes from region to region and turns as a unit turns, which map rush measures by walking a unit in the game. Over nine maps (seven of Blizzard's and two from map generate, 103 walks with a Zergling), the ground distance here was within 2.5% of the game's walk on average and 8% at most. The game's walk is usually a little longer, so the seconds here are a few percent quicker than map rush's. Use this command to see a layout in a second while you work, and map rush to time it in the game.

The command exits with 2 for a map with fewer than two start locations, and with 1 when no copy of the game is found.

Rush distances#

scmjs map rush measures how long a rush takes between each pair of start locations. The game walks a unit from each start location to every other, along the path a unit sent there in a game would take, and times each walk. An SCV walks unless you name another unit with --unit: by its name in the editor ("Zerg Zergling"), without the race (Zergling, Dragoon), or by its number in units.dat. The rows of the table are the starts walked from and the columns the starts walked to, each with its place on the map as a clock face from the middle:

$ scmjs map rush "(4)Crossing.scx" --unit Zergling

The pixels are the distance the unit walked (32 to a tile) and the seconds are game time at Fastest. The unit sets out five tiles from its start toward the middle of the map and stops at the edge of the town hall at the other start: a neutral Nexus stands on every start while the walks run, so the walk ends where a real rush ends, at the base. The two directions between a pair can differ by a second or so, because the way out of each base is not the same. The shortest and longest walks are compared with the straight line between the two starts, the distance a flyer goes. When the terminal is too narrow for both figures, the seconds and the pixels come as two tables.

A walk that does not arrive is a finding too. Two starts with no ground between them, on an island map or where the terrain walls one off, are reported as having no way; on a map where no two starts are joined, the report says so and lists the straight lines instead. A unit that stops short (at a wall of minerals or buildings the map places, say), gets stuck, or is still walking after seven minutes of game time is named with how far from the base it ended.

The walks run in one game with nobody else in it: about four seconds for a four-player map and fifteen for an eight-player map of 256 × 256. --seed changes the game's luck, such as a unit stepping round another; the default is the one the editor's Walkability plugin uses, so the two agree. --json gives every walk and the table as data. A building or a flyer is refused (exit 2), as is a map with fewer than two start locations. map analyze gives the same distances in a second without the game, within a few percent, beside the map's naturals and narrow points.

Is the map fair to every start#

scmjs map balance is a melee map's report card. The same two sides play game after game on the map, and the report has a row for each start location: how often the side that started there won, how long its games lasted and how soon it met the enemy, beside the numbers that need no game. The sides are your bots: one bot plays the game's own computer, or two bots play each other, as bot ladder plays them.

scmjs map balance "(4)Crossing.scx" --bots out/mybot.scmbot:p --races p --games 12 --parallel 4
scmjs map balance "(4)Crossing.scx" --bots mybot.scmbot,mybot.scmbot --games 12

Column Means
Games, Won, Lost The games a side started at this start location, and how they went. A game stopped at --frames is counted in Games only
Win rate Won out of won and lost
Expected What the two sides' own records predict for those games. With two sides of a strength it is 50%; when one side is stronger, a start it was dealt more often is expected to win more
Length, Contact The average game, and the average time the first unit was lost to the other side
Rush The average walk to the other starts, as map rush measures it; --no-rush leaves it out
Minerals, Gas The main's fields and geysers: those nearest this start and within 12 tiles of it, the amount each holds and their average distance in tiles

The verdict compares each start's win rate with what was expected. Within 10 points everywhere, the map is called balanced within the largest difference. A start further off is named, with the number that sets it apart from the others when one does (less gas, a mineral line further away, shorter walks to the enemy, earlier fights). When the games are too few to tell the difference from chance, the verdict says so and how far chance alone would move that start. When one side won every game, the games say nothing about the starts, and the verdict asks for two sides of a strength: the same bot twice does that.

The game deals the start locations itself, as it does in any melee game, and there is no way yet to ask for a particular one. So each game's replay is played back afterwards to see which start each side was dealt, and the rows are filled from those. Enough games give every start its turn; the line under the table lists the pairs of starts that met and those that never did. A bot playing itself plays each seed once, since the other lobby order deals the same starts and gives nearly the same game.

A game takes from ten seconds to a minute or so, depending on the bots and how long it lasts; --parallel plays several at once (by default up to four, as the computer's cores and memory allow; a game takes about 1.5 GB for each bot in it). The replays are deleted afterwards unless --out names a folder to keep them in, for scmjs replay watch. --json gives every row, every game with the starts dealt, and the verdict as data. The command exits with 1 when a game could not be played, and with 2 for a map with fewer than two start locations.
