Changing a map

Each command here writes the map back over itself, or to another file with --out other.scx, and keeps everything else in the file as it was: its sounds and other files, and the way the scenario was compressed, as Save does in the editor. A sound StarEdit stored with the game's own sound compression stays stored that way while it is unchanged, so the file does not grow. A folder in the --out path that is not there yet is made. When the command succeeds, a file --out names is always written, changed or not, so the next step of a script finds it; --out - sends the map to standard output.

Name, description and revision#

scmjs map set is Map Properties. It sets what you give and leaves the rest, and writes nothing when nothing changed.

scmjs map set ridge.scx --name "Ridge <04>2.1" --description "Final for the tournament."
scmjs map set ridge.scx --revision remastered
scmjs map set ridge.scx --encoding euc-kr

$ scmjs map set ridge.scx --name "Ridge 2.1"
✔ ridge.scx: Name Ridge → Ridge 2.1 · written to ridge.scx · 3.0 KB

In a name or description, <XX> is one of the game's colour codes, as in the string files. --revision is one of original, hybrid, broodwar, remastered and remasteredHybrid, and does what the editor's revision change does. --encoding is how the map's text is stored for 1.16.1: utf-8, euc-kr (CP949), shift_jis, gbk, big5, windows-1251 or windows-1252. Remastered reads UTF-8. Both take any case. Text that is plain ASCII is the same in every encoding, and a map does not record which one it was written in, so on such a map --encoding has nothing to change; the command says so and writes nothing. --dry-run says what would change and writes nothing.

Players, forces and other settings#

scmjs map settings lists the Scenario menu's settings as a map has them: the twelve players, the four forces, the unit types, upgrades and technologies the map changes from the game's, and the switches it names.

ums.scx
Players
  player  type      race      colour  force
  1       Human     Terran    Red     1 Defenders
  2       Computer  Zerg      Blue    2 Swarm
  3       Inactive  Inactive  Teal    1 Defenders
  …
Forces
  force  name       players              allied  allied victory  shared vision  random start
  1      Defenders  1, 3, 4, 5, 6, 7, 8  yes     yes             yes            no
  2      Swarm      2                    yes     yes             yes            no
  …
Unit settings
  Terran Marine  0  named "Test Marine" · 80 hit points, armor 2, build time 300, 75 minerals, 0 gas
Upgrades: as the game has them
Technologies: as the game has them
Switches: 1 "Alarm raised"

A unit, upgrade or technology is listed when the map gives it numbers or a name of its own, or changes who may build or research it. --unit <name>, --upgrade <name> and --tech <name> show one row whether the map changes it or not, with the game's own numbers beside the map's when your copy of StarCraft is there to read them from. --json has every row with each player's availability, levels and state.

scmjs map set --settings <file> sets them. The file is a JSON object with any of six lists, and each entry names what it changes and gives only the fields to change:

{
  "players": [{ "player": 3, "type": "Computer", "race": "Protoss", "force": 2 }],
  "forces": [{ "force": 2, "name": "Invaders", "randomStart": true }],
  "units": [
    { "unit": "Zergling", "hitPoints": 50, "name": "Ripper" },
    { "unit": "Terran Ghost", "available": [{ "player": "default", "value": false }, { "player": 1, "value": true }] }
  ],
  "techs": [{ "tech": "Stim Packs", "state": [{ "player": 1, "researched": true }] }],
  "switches": [{ "switch": 2, "name": "Gate is open" }]
}

$ scmjs map set ums.scx --settings settings.json
  Player 3       type                     Inactive → Computer
  Player 3       race                     Inactive → Protoss
  Player 3       force                    1 → 2
  Force 2        name                     Swarm → Invaders
  Force 2        random start             no → yes
  Zerg Zergling  name                     (none) → Ripper
  Zerg Zergling  uses the game's numbers  yes → no
  Zerg Zergling  hit points               35 → 50
  Terran Ghost   available by default     yes → no
  Terran Ghost   available to Player 1    default → yes
  Stim Packs     for Player 1             default → researched
  Switch 2       name                     (none) → Gate is open
✔ ums.scx: 12 settings changed · written to ums.scx · 4.0 KB
List Each entry
players player (1 to 12), then type, race, color and force (1 to 4). A colour is a name such as Red, a number, or [r, g, b] for a Remastered custom colour. Colour and force are for players 1 to 8
forces force (1 to 4), then name, players (moved into the force), allied, alliedVictory, sharedVision, randomStart
units unit (a name or id), then name, hitPoints, shields, armor, buildTime, mineralCost, gasCost, weapons (each weapon, damage, bonus), available, useDefault
upgrades upgrade (a name or id), then mineralCost, gasCost, timeCost, the amount each grows by a level (mineralFactor, gasFactor, timeFactor), levels, useDefault
techs tech (a name or id), then mineralCost, gasCost, researchTime, energyCost, state, useDefault
switches switch (1 to 256) and name; an empty name clears it
  • Times are in frames, 24 to a second.
  • available, levels and state are lists with one entry a player: player is 1 to 12, or "default" for the column every player follows until given a value of their own. An available entry has value (true, false, or "default" to follow that column again), a levels entry start and max, a state entry available and researched.
  • A number for a unit, upgrade or technology takes it off the game's own numbers, as unticking "use default" does in the editor, and the rest of its row is filled in from the game's tables. Those settings read your copy of StarCraft; names, availability, levels, players, forces and switches need none. "useDefault": true puts a row back on the game's numbers.
  • A weapon is one the unit fights with: the Zergling's is Claws. Another is refused.

Every name is checked before anything is set. One the map or the game does not have stops the command with the entry's place, and nothing is written:

$ scmjs map set ums.scx --settings bad.json
✖ players[1]: No race is called "Zergg"
  One of Zerg, Terran, Protoss, User Selectable, Random, Independent, Neutral, Inactive. Nothing was changed.

--settings goes with --name and the other options in one command, --settings - reads the JSON from standard input, and --dry-run lists the changes and writes nothing. Sounds and the Create Unit with Properties slots are not set from here; the editor has them.

Resizing#

scmjs map resize ridge.scx --size 128x96 is Scenario ▸ Resize.

✔ ridge.scx: 96 × 64 → 128 × 96 · written to ridge.scx · 3.6 KB

--anchor says which part of the map stays where it is: center (the default), top-left, top, top-right, left, right, bottom-left, bottom or bottom-right. Units and other things that fall outside the new edge are dropped, and the command lists them, twenty at most unless you pass --all; a start location that is dropped is always named, on a line of its own. Locations that hang over the edge are pulled inside unless you pass --no-clamp; the command names a location that came out of that with no width or height, or, with --no-clamp, one left past the edge. New ground is the tileset's base terrain. --dry-run says what would happen and writes nothing.

Listing units and locations#

scmjs map units lists the units placed on a map, and scmjs map locations its locations. They are the lists to read before map edit: a unit is named there by its index, a location by its name or number.

$ scmjs map units ums.scx --player 1
ums.scx  5 of 21 units
  index  unit                   player    x,y       tile
  0      Start Location         Player 1  336,1744  10,54
  16     Terran Command Center  Player 1  336,1744  10,54
  17     Terran Marine          Player 1  464,1616  14,50  hp 50%
  18     Terran Ghost           Player 1  496,1616  15,50  energy 75%, cloaked
  19     Protoss Carrier        Player 1  592,1552  18,48  hangar 4

$ scmjs map locations ums.scx
ums.scx  3 locations, and Anywhere
  number  name      pixels             tiles        units
  1       Base      192,1600–512,1856  6,50–16,58   4
  2       Nest      1536,192–1856,512  48,6–58,16   2
  3       Middle    896,896–1152,1152  28,28–36,36  0
  64      Anywhere  0,0–2048,2048      0,0–64,64    21
Option of map units What it does
--unit <name> Only this type: a name such as "Terran Marine" or Zergling, or a units.dat id
--player <n> Only this player's units, 1 to 12; 12 is neutral
--location <name> Only units inside this location, by name or number
--rect <l,t,r,b> Only units inside this rectangle, in pixels
--tiles <x0,y0,x1,y1> Only units inside this rectangle, in tiles
--all Every row; a long list is cut at 40 otherwise
--json The rows as data, never cut

A unit's index is its place in the file, counted from 0. A location's number is the one triggers and map dump use, counted from 1. A unit is inside an area when its centre is, and the right and bottom edges of a rectangle are just outside it. The last column holds what the unit's record sets: resources, hit points, shields and energy in percent, the hangar, and the states cloaked, burrowed, lifted, hallucinated and invincible. With several filters, a unit must pass all of them. map locations has no options but --json; its last column counts the units inside each location.

Listing terrain and doodads#

scmjs map terrain lists the terrains of the map's tileset and draws the map as a grid of letters, and scmjs map doodads lists the doodads on it. They are the lists to read before painting terrain or placing doodads. Both read the tileset from your copy of StarCraft.

$ scmjs map terrain ridge.scx --cell 2
ridge.scx  64 × 64 · Jungle World
  letter  terrain             id  height  buildable  tiles  share
  w       Water               5   low     no         1,130  28%
  d       Dirt                2   low     yes        1,710  42%

  …
  D       High Dirt           3   mid     yes        444    11%
  U       High Jungle         10  mid     yes        0      0
  …

  * 24 tiles of a doodad

  Tiles 0,0 to 64,64, a character every 2 tiles
     0         20        40        60
   0 ddd#ww##d#www##ddd#wwwwwwwwwwwww
   2 dddd##ddd#wwww##ddd#wwwwwwwwwwww
  …
  16 ddddddddddddddDDDDddddd#wwwww###
  18 ddddddddddddDDDDDDDDddd#wwwwwwww
  20 ddddddddddd#DDDDDDDDD#d#wwwwwwww
  22 ddddddddddDDDDDDDDDDDDdd#wwwwww#
  …

A terrain's height is low, mid or high, and a cliff forms where two heights meet. Its letter is lower case for low ground and upper case above it. In the grid each character is the terrain most of its cell is; # is the edge between two terrains, a cliff or a shore, and * a doodad. The grid is kept to 64 columns, so a 128-tile map is drawn a character every 2 tiles; --cell 1 with an area draws every tile of it.

Option of map terrain What it does
--tiles <x0,y0,x1,y1>, --rect <l,t,r,b>, --location <name> Only this area: the counts and the grid
--cell <n> Tiles a character of the grid
--no-grid The table alone
--starcraft <folder> Your copy of the game, when it is not in one of the usual places
--json The terrains, the counts and the grid's rows as data 
$ scmjs map doodads ridge.scx --category ramp
ridge.scx  1 of 23 doodads · Jungle World
  index  doodad            id  tile   size
  0      Cliff #13 (ramp)  13  32,38  6 × 6

ℹ 102 doodads to place
  id   doodad                   size   goes on
  12   Cliff #12 (ramp)         6 × 6  High Dirt, Dirt, cliff or shore pieces
  13   Cliff #13 (ramp)         6 × 6  High Dirt, Dirt, cliff or shore pieces
  …

A doodad has no name of its own: it is its category and its id, "Cliff #13". Its index is its place in the file, counted from 0, and its tile is its top-left corner. Without an option the command lists the doodads on the map and the tileset's categories. --category <name> narrows the list to one category and adds the doodads of it that can be placed, each with its size and the ground it goes on; --category ramp is the ramps of every category. --palette lists every doodad the tileset has. The area options keep the placed doodads whose centre is inside, and --all lifts the cut at 40 rows.

Editing units, locations, sprites and fog#

scmjs map edit applies a list of edits to a map: its units, locations, sprites and fog of war, and its terrain and doodads. The list is a JSON file, so it suits a script or an AI tool more than typing by hand. The edits are applied together: when one of them cannot be done, nothing is written.

[
  { "op": "place_unit", "unit": "Terran Marine", "player": 1, "x": 400, "y": 1700 },
  { "op": "update_units", "where": { "unit": "Terran Marine", "location": "Base" }, "invincible": true },
  { "op": "remove_units", "indices": [20] },
  { "op": "add_location", "name": "Ramp", "tiles": { "x0": 20, "y0": 40, "x1": 24, "y1": 44 } },
  { "op": "edit_location", "location": "Middle", "name": "Centre" }
]

$ scmjs map edit ums.scx --edits edits.json --out ums-edited.scx
  0  place_unit     Terran Marine · Player 1 · 400,1700 · unit 20
  1  update_units   2 units changed
  2  remove_units   1 unit removed
  3  add_location   4  Ramp · 640,1280–768,1408
  4  edit_location  3  Centre · 896,896–1152,1152
✔ ums.scx: 5 edits · 1 setting changed, 2 units added, 2 units removed, 1 location added, 1 location changed, 2 strings added · written to ums-edited.scx · 4.0 KB

Each line is one edit: its place in the list, its kind, and what it did. A placed unit or sprite is shown with the index it has in the written map, a new location with its number. The last line counts the change as map diff does, where a changed unit counts as one removed and one added.

Option What it does
--edits <file> The edits: a JSON list, or an object with the list as edits; - reads it from standard input
--out <map> Write the result here instead of over the map; - for standard output
--dry-run Print the change as map diff prints it, and write nothing
--all List every edit and every change; long lists are cut otherwise
--starcraft <folder> Your copy of the game, for the edits that read it, when it is not in one of the usual places
--json What each edit did and the comparison, as data
Kind of edit (op) Its fields
place_unit unit, player, a position, and any unit properties; snap and check
move_units Units, then a position (for one unit) or dx and dy in pixels (for any number)
update_units Units, then player (the new owner) and any unit properties
remove_units Units
add_location name, and rect or tiles
edit_location location, then name, rect or tiles
remove_locations locations, a list of names or numbers
place_sprite sprite (a sprites.dat id) or unit (a unit drawn as a sprite), then player, a position, flipped, disabled
remove_sprites indices, or where with any of sprite, unit, player and an area
set_fog players (a list of 1 to 8), mode (fog or clear), and an area; the whole map without one
paint_terrain, place_doodad, scatter_doodads, remove_doodads Terrain and doodads
  • A unit type is a name ("Terran Marine", "Zergling") or a units.dat id. A player is 1 to 12; 12 is neutral.
  • A position is x and y in pixels, or tileX and tileY for the centre of a tile.
  • An area is one of rect (left, top, right, bottom in pixels), tiles (x0, y0, x1, y1) or location (a name or number).
  • Units are named by indices, as map units lists them, or by where: any of unit, player and an area, all of which must hold.
  • Unit properties are hitPoints, shields and energy in percent, resources, hangar, and the states cloaked, burrowed, lifted, hallucinated and invincible, each true or false. Only what you give is changed.

An index always means the map as it was before the edits, so removing unit 3 early in the list does not shift what "indices": [17] means later in it. A where looks at the map as the earlier edits left it, units placed by them included. A where that matches nothing is not an error; the edit's line says "no unit matches".

An edit that cannot be done stops the list. The error names it by its place in the list, counted from 0, and the map is left alone:

$ scmjs map edit ums.scx --edits bad.json
✖ edits[1] (remove_units): there is no unit 99: the map's units are 0 to 20
  Nothing was changed: the edits are applied together or not at all.

Edits that are refused include a unit or location name the map does not have, an index past the end or already removed by an earlier edit, a position or rectangle off the map, a field the kind of edit does not take, a second location with a name already in use, and any change to Anywhere. A file that is not JSON, or an entry that is not an edit, exits 2; an edit the map refuses exits 1.

A unit's position is used as given, and nothing is checked against the terrain or other units, unless the edit asks. Both of these read the unit tables and the tileset from your copy of StarCraft:

  • "snap": true puts a building on the building grid, as the editor places it. Without it, give the building's centre in pixels: a Command Center is 4 by 3 tiles, so with its top-left corner at tile 8,52 its centre is 320,1712.
  • "check": true refuses a position the editor would refuse: unwalkable ground for a unit, unbuildable ground for a building, another unit in the way.

A list with neither, and with no terrain or doodad edit, needs no copy of the game.

A sprite is placed by its sprites.dat id, or as a unit sprite by the unit's name. Fog is set per tile, so an area in pixels covers every tile it touches. The edits go through the editor's own plugin host, the one map run uses, so a unit or location is written as a plugin's api.document.edit would write it.

Painting terrain and placing doodads#

Four kinds of edit change the ground. They go in the same list as the others, and they read the tileset from your copy of StarCraft. This list turns a flat map into the one pictured: lakes, a plateau with a ramp down, and rubble.

[
  { "op": "paint_terrain", "terrain": "Water", "cover": 0.12, "grain": 10, "seed": 7, "symmetry": "rot180" },
  { "op": "paint_terrain", "terrain": "High Dirt", "tiles": { "x0": 20, "y0": 16, "x1": 44, "y1": 40 }, "shape": "ellipse" },
  { "op": "place_doodad", "doodad": "ramp", "tileX": 30, "tileY": 38, "within": 8 },
  { "op": "scatter_doodads", "doodad": "Dirt", "density": 0.03, "seed": 3 }
]

$ scmjs map edit ridge.scx --edits terrain.json
  0  paint_terrain    Water · 2,080 tiles changed
  1  paint_terrain    High Dirt · 788 tiles changed
  2  place_doodad     Cliff #13 · 32,38 · 6 × 6 · doodad 0
  3  scatter_doodads  22 doodads placed
✔ ridge.scx: 4 edits · 5 sections changed · written to ridge.scx · 12 KB

Kind of edit (op) Its fields
paint_terrain terrain, and an area (the whole map without one); shape, cover, grain, seed, symmetry
place_doodad doodad, and tileX and tileY, its top-left tile; within, force, seed
scatter_doodads doodad, and an area (the whole map without one); count or density, seed
remove_doodads indices, as map doodads lists them, or where with doodad and an area

Terrain is a name or id that map terrain lists. It is painted with the editor's isometric brush, so the edge forms on its own: a cliff where the height changes, a shore beside water. A plateau is high ground painted on low ground. The brush works on diamonds four tiles wide and two high, so an area is painted to the nearest diamond and its outline is the brush's.

Field of paint_terrain What it does
shape rect, the area itself, or ellipse, the ellipse inside it
cover From 0 to 1: paint that share of the area, in patches, instead of all of it
grain How large a patch is, about, in tiles: 8 without it
seed Where the patches fall. The same seed paints the same patches
symmetry Repeat the stroke at its images: h (left and right), v (top and bottom), hv (all four), rot180, and on a square map rot90, diag and adiag

A doodad is an id, a name such as "Jungle #180", a category's name for any one of its doodads, or ramp for whichever of the tileset's ramps fits. place_doodad is refused where StarEdit would refuse it: a doodad goes on the ground it is drawn for, and a ramp only on the cliff shape it was drawn for. within says how many tiles around to look for a place where one fits, which is the way to place a ramp: paint the plateau, then ask for ramp within a few tiles of its edge. force places one doodad, named by its id, whatever is under it.

scatter_doodads places count doodads, or as many as cover the density share of the area's tiles (0.1 without either), each where it fits and whole inside the area. A category scatters a mix of its doodads. When no more fit, fewer are placed, and the line says so. remove_doodads puts the ground under a doodad back.

Painting terrain does not move what stands on it: a unit can end up in a lake, or a start location on a cliff. Look at the result with map preview and run map check. A map without the isometric lattice, as some older editors leave it, cannot be painted by type until the editor's Terrain palette rebuilds it; map terrain says when that is so. Repeating a list paints the same terrains in the same places, but the tiles can differ, since the brush picks among a terrain's variations at random.

Triggers and strings as text#

A map's triggers and strings can live beside it as text files. In git a change to them shows as a diff; in any text editor you can search and replace across a hundred triggers. Then they go back into the map.

scmjs map triggers export mymap.scx > triggers.txt
scmjs map triggers import mymap.scx triggers.txt

triggers export prints the triggers in the text form the editor's trigger window uses (the trigger reference lists every condition and action in it), or writes them to --out. A file name ending in .trg writes the raw trigger records instead: the file SCMDraft's Export Triggers makes and reads. --briefing exports the mission briefing's triggers.

triggers import replaces the map's triggers with the file's, or adds them after the map's own with --append. Text the map cannot resolve, such as a condition it does not know or a location it does not have, is refused with its line number, and nothing is written. A file with no triggers in it is refused too (exit 2), since importing it would take every trigger out of the map, as an export that failed and left an empty file would; --allow-empty imports it when that is what you mean. A .trg of a mission briefing is refused as triggers, and one of triggers with --briefing. - as the file reads the text from standard input, so one map's triggers can go straight into another:

scmjs map triggers export a.scx | scmjs map triggers import b.scx -

scmjs map strings export mymap.scx > strings.txt
scmjs map strings import mymap.scx strings.txt

The strings file has one string a line: the string's number, a tab, and its text, with the game's colour codes written as <XX>. A # starts a comment. strings import sets each numbered string in place and adds any numbered past the end. Nothing is renumbered, because the map's triggers and locations refer to strings by number; a line you take out leaves that string as it is. A file with no strings in it, or one that gives a number on two lines, is refused.

Both imports take - for standard input, --dry-run to say what would change and write nothing, and --json for the result as JSON.

Editing triggers or strings in your editor#

edit exports, opens the text in your editor, and imports it when you close the editor:

scmjs map triggers edit mymap.scx
scmjs map strings edit mymap.scx --editor "code --wait"

The command waits until the editor is closed. If you saved a change, the text is imported as import reads it and the map is written. If you saved nothing, or only a comment, the map is left alone and the command says nothing changed.

Text that cannot be read, such as a condition the map does not know or a strings line that is not a number and a tab, is not imported and the map is left alone. The error gives the line. The file you edited is kept with your changes in it, and the command prints its path and the import command that brings it in once you have fixed it. The same happens when the map cannot be written, such as a read-only file: your text is kept, and the command says how to bring it in. Taking every trigger out in the editor takes them out of the map; taking every string line out changes nothing. --json gives the result as JSON.

The editor is --editor, or else the VISUAL or EDITOR setting as git uses them, or else Notepad on Windows and vi elsewhere. An editor that opens a window has to be told to wait for it to close, or the command sees the file unchanged straight away: code --wait, subl -w, gedit -s. triggers edit --briefing edits the briefing's triggers. An empty --editor is refused, and so is vi when the command has no terminal to give it (in a script or a pipe), rather than waiting for keys that never come.

Removing unused strings#

scmjs map strings prune ridge.scx is the string editor's Delete Unused. A string that no trigger, location, name, force, sound or setting refers to is blanked, and the blank slots at the end of the table are dropped. Nothing is renumbered, so the triggers still point at the right strings. --dry-run lists what would go and writes nothing; with --out, the map is written there even when nothing went.

Making a map smaller#

scmjs map optimize takes out of a map what the game never uses and stores the rest as small as the game still reads it. It writes over the map unless --out names another file; --dry-run says what would go and writes nothing. A table says what each step saved:

$ scmjs map optimize "(3)Defenders of the Galaxy.scm"
✔ (3)Defenders of the Galaxy.scm: 44 KB → 36 KB (−17.7%) · written to (3)Defenders of the Galaxy.scm

  Step                                           Saved
  Unused sounds    none                          -
  Other files      none                          -
  Unused strings   23 strings                    243 B
  Editor sections  skipped: with --strip-editor  -
  Compression      PKWARE, rewritten             7.5 KB

Removed
  string    21 - Defend your Nexus at all costs.  nothing in the map refers to it
  …

In order, the steps are:

  • Sounds that no trigger or briefing plays and the sound list does not name, and the sound list's entries for files the map does not hold. A sound only the list names stays: it is in the Sound Editor, waiting for a trigger.
  • Any other file in the archive that nothing in the map names, listed one by one.
  • The strings nothing refers to, as strings prune drops them.
  • With --strip-editor, the sections only editors read (below).
  • Every file compressed again. PKWARE is the default, since every version of the game reads it. A map that was already in zlib, which only Remastered reads, gets the smaller of the two. --compression zlib or --compression pkware chooses, and the map is then written in it even when that comes out larger: that is what the file is for.

Some files stay whatever refers to them. The game itself opens a few files by name: (attributes), (signature) and the marks Blizzard's own maps and the ladder maps carry, such as blizzard_2.cnd. TrigScript's, Magenta's and the editor's build files stay (trigscript\, magenta\, scmjs\), as do files the archive holds without a name. A sound StarEdit imported is stored with the game's own sound compression, which loses a little quality to be about four times smaller; the editor reads it but cannot write it, and writing it any other way would make the map larger, so such a file is kept exactly as it is stored. A file stored in zlib is not kept that way in a map written with PKWARE, since 1.16.1 could not read it. --keep names another file to keep, once per file: --keep "notes\" keeps a folder. The command tells you when the map has no file of a name --keep gives.

A map built from a TrigScript script keeps its scenario as it was built, so the editor still opens the map you were editing; only its stray files and its compression change. A map whose triggers write to the game's memory (an EUD map) keeps every string, since such a map can reach a string by its place in the table.

--strip-editor also drops ISOM, TILE, DD2, IVER, IVE2, IOWN, UPUS, SWNM and WAV, the sections the CHK reference marks as read by editors only, with the strings and sounds only they named. The map plays the same, but an editor that opens it has no isometric terrain to paint, no doodads to select, no sound list and no switch names. It is the Save dialog's Smallest that plays for these sections; keep the original to go on editing.

The result is opened again as the editor opens a map before anything is written, and when the editor cannot write the map any smaller, nothing is written over it; --out, or standard output when the map came from a pipe, still gets the map, as it was, and the list is headed Would go. scmjs map diff between the two shows only what went.

The archive as a folder#

A map file is an archive: the scenario, staredit\scenario.chk, with the map's sounds, a TrigScript script's files and anything else put in it. scmjs map unpack writes those files into a folder at their paths in the archive, and scmjs map pack puts the folder back together:

scmjs map unpack ridge.scx            # → ridge/staredit/scenario.chk, ridge/staredit/wav/…, ridge/archive.json
scmjs map unpack ridge.scx --list     # the files and their sizes, nothing written
scmjs map pack ridge                  # → ridge.scx again, beside the folder

archive.json in the folder records what the files cannot: the map's name, how the scenario was compressed and whether it was encrypted, whether the archive had a file list, and the files a protected map keeps without a name, which go under stored/ byte for byte. pack writes the archive as archive.json says, so an unpacked and repacked map reads the same in the editor and the game.

A sound StarEdit stored with the game's own sound compression comes out as a plain WAV, with its stored form kept under stored/ beside it; pack puts back the stored form while the WAV is the one unpack wrote, so the map does not grow. A sound you changed goes in as plain PCM, which is larger, and pack says so; map optimize cannot make it smaller again. A folder with such sounds has archive.json version 3, which scmjs before 0.13.4 refuses rather than packing wrongly.

A file you add to the folder goes into the map at its path: a sound dropped into staredit/wav/, a script's file under trigscript/. --compression none|pkware|zlib changes how every file is stored, and --out names the folder or the file to write. pack --out - writes the map to standard output; pack --dry-run builds and checks it and writes nothing.

unpack never mixes two maps in one folder. Unpacking a map again over its own earlier unpack replaces it, and a file the map no longer has is removed. A folder that holds another map's unpack, or files changed or added since the unpack, is refused unless you pass --force, so an edit is not thrown away without a word; a folder that holds other files altogether is refused even then. --out - is refused, since unpack writes a folder.

Nothing is parsed or restored on the way: the folder is the file as it is. A map the editor built from a TrigScript script unpacks into its built scenario and the scmjs/ files holding the source, and packs back into the same built map. The packed file is opened as a map before it is written, so a folder whose scenario is not a scenario is refused (exit 2).

With --text, the scenario itself is written as text files under scenario/ instead of the one binary staredit/scenario.chk, so the map can be kept in git and read and merged as text. A map as a folder of text explains the folder.

Building a TrigScript map#

The editor builds a map with a TrigScript script every time it saves it: the script's trigger() calls become triggers in the map, and its program()s are built into the file. scmjs map build does the same without the editor, so a map kept in git can be built where it is checked, and a script edited outside the editor can be applied from the terminal.

$ scmjs map build maps/ridge.scx --test
✔ ridge.scx: 12 triggers → #4–#15 · 2 programs (Remastered) · 7 tests passed · written to maps/ridge.scx · 48 KB  TrigScript 4.4.0, TypeScript 6.0.3

The line ends with the versions of TrigScript and TypeScript that built the map.

The script is the one the map keeps, with the copies of libraries the map keeps. It is compiled against the map's names, settings and placed units, as the editor compiles it. The built file opens in the editor as the map you were editing, with the build kept beside it, as a saved one does.

Option What it does
--out Writes the built map to another file
--test Runs the script's tests first, in the simulator; a failing test stops the build. A map whose script settings make tests guard the build runs them without the flag
--check Compiles (and tests, with --test) and writes nothing: the check for a pull request

An error in the script is printed as main.ts:12:5 error …, a failing test with its name and line, and the command exits with 1 with nothing written.

The compiler is TrigScript's own, the version this release of the editor ships, so the command and the editor build the same map. It compiles with TypeScript 6, which is not part of the command: install it in the map's project (npm install typescript@6) or globally (npm install -g typescript@6). A sound of two seconds or more is encoded as Ogg Vorbis with an encoder the command fetches once, unless the project has wasm-media-encoders installed.

Two things differ from the editor. In the tests, a unit type's hit points come only from the map's own unit settings: the editor falls back on the game's unit data for a type the map leaves at its defaults, and the command does not have that data. A test that counts on a Marine's 40 hit points should set them in the map. And programs that other plugins add to a build are not built here: a map with Magenta's triggers is refused, and is built by saving it in the editor.

A map's script as files#

A map with a script keeps the script's files inside it. scmjs map script takes them out and puts them in, so a script can be written in any editor and a map can be given one without opening the editor. import puts files into the map and says at once whether the script compiles:

$ scmjs map script import ridge.scx script/
ridge.scx: arrive.ts, main.ts added · written to ridge.scx · 4.3 KB
main.ts:4:18 error Property 'Gate' does not exist on type '{ … readonly Base: Location<1>; readonly Nest: Location<2>; readonly Middle: Location<3>; … }'.
✖ 1 error in the script. The files are kept in the map: import the corrected ones.

The script named a location the map does not have, and the error lists the ones it has. The files are in the map all the same, so the corrected file alone is enough:

$ scmjs map script import ridge.scx script/main.ts
ridge.scx: main.ts changed · written to ridge.scx · 4.3 KB
✔ compiles: 2 triggers · TrigScript 4.5.0, TypeScript 6.0.3
The map's triggers are as they were: scmjs map build applies the script.

Importing never changes the map's triggers. scmjs map build makes them from the script.

A file goes in under its own name, so script/main.ts is main.ts. A folder gives every .ts and .tsx file in it at its path inside the folder, so script/quests/shop.ts is quests/shop.ts; declaration files and node_modules are passed over. - reads main.ts from standard input. A script starts at main.ts, and the other files are imported from it. Files that are not named stay as they are; --remove quests/old.ts takes one out. The command exits with 1 when the script does not compile, and --out writes the map to another file.

export gives the files back. With no folder it prints them, each under a line with its name when there is more than one, and says on standard error how the script stands to the map's triggers. Naming files prints only those, and --out writes them into a folder:

$ scmjs map script export ridge.scx --out script
✔ ridge.scx: 2 files, 362 B · applied: triggers #4 to #5 of the map are this script's
  main.ts → script/main.ts
  arrive.ts → script/arrive.ts

"Applied" means the map's triggers are what the files compile to. "Not applied" means the files changed since the last build, or were never built.

api looks up what a script can call. With no words it lists every function, type and table by name; with words it prints the declarations that hold all of them, each with its documentation. --map uses that map's own names, so its locations, switches and sounds are there as a script writes them:

$ scmjs map script api bring --map ridge.scx
// ── Conditions ──
/** Bring — Player, Unit, Location, Comparison, Amount */
declare function bring(player: Player, unit: UnitType, location: Location, comparison: Comparison | number, amount: number): Condition;
…

The TrigScript guide explains the language. For a script with media files, or to see every file of the archive, use map unpack.

Running a plugin over a map#

scmjs map run gives a plugin the editor's plugin API with a map open and no editor around it. The plugin can be a folder with a plugin.json, the manifest itself, a single script file, github:owner/repo or a URL: whatever Plugins ▸ Add takes, and a file on your disk too. A script is a file that exports activate(api) as a plugin's entry does, so a few lines that read or change a map need no plugin around them:

// starts.mjs
export default (api) => {
  const starts = api.document.scenario().units.filter((u) => u.unitId === 214);
  api.ui.status(`${api.document.info().name}: ${starts.length} start locations`);
};

$ scmjs map run starts.mjs "(4)Crossing.scx"
ℹ Crossing: 4 start locations
✔ (4)Crossing.scx: starts ran · the map is unchanged

A script that changes the map, run with --dry-run to see the change first:

// gate.mjs
export default (api) => {
  api.document.update("Name switch 1", (tx) => tx.switches.setName(0, "Gate is open"));
};

$ scmjs map run gate.mjs ridge.scx --dry-run
…
✔ ridge.scx: gate ran · 1 setting changed, 1 string added · not written (--dry-run)

What the plugin would show is printed as it happens: its status line, its toasts, and the warnings and errors in its log. Dialogs and panels register and show nothing, and a request for a file gets none. What the plugin writes to the console goes to standard error, an error as one line, so standard output holds only the command's own result. --command <id> runs one of the commands the plugin registered, with --arg values as its arguments (--arg without --command is refused); --json includes what the command returned. A command that starts its work and returns without waiting for it is waited for: the command line waits until the timers and file reads the plugin set off are done, ten seconds at most. A plugin that shows its findings only in a dialog, as Repair's Repair Map… does, shows nothing here.

A folder whose plugin.json names a build that is not there yet (a plugin cloned and not built) is run from its source, as scmjs plugin dev serves it. A path that is not there, a file that is not a plugin and a folder without a plugin.json are each said in one line (exit 2).

The map is written back only when the plugin changed it (--out writes it elsewhere, even unchanged, and a map read from - always goes on to standard output), and the last line says what changed, in the terms of map diff. --dry-run prints that comparison in full and writes nothing. Saving is the command's job: api.document.save() writes nothing and resolves true, since the command writes the map at the end, and api.document.saveAs() resolves false, having no dialog to show. A plugin written in TypeScript needs TypeScript installed, as map build does; a built plugin or a JavaScript script needs nothing more.

With a copy of StarCraft on the computer, the plugin has the game's data as it does in the editor: the map's tileset, so the terrain types, the isometric brush and the doodads work, and the unit tables, so a unit's size and the placement check do. api.tileset.load() and api.data.load() answer true. Without a copy, those parts of the API do nothing and leave a note saying what they needed, and everything else works as before. --starcraft <folder> names the copy, and --no-game runs without one, which is how the plugin will run on a build server. --json says which copy was used.

This is the editor's own plugin host, so a plugin's logic runs as it does in the editor. You can try a plugin from a terminal, or run it over many maps from a shell loop, before anyone installs it.
